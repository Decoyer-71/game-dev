## 0. ⚠⚠ 이 화면의 목적은 하나다 — **범위 대가 `T` 를 확정할 수 있게 하는 것**

예쁜 전투 연출이 아니다. 목적을 이렇게 좁히는 근거가 문서에 이미 있다:

| 어디 | 무엇 |
|---|---|
| HANDOFF §4-15 | `ScopeDamageBudget`(**T = 1.15**)·`ScopeDamageBudgetLegion`(**T만 = 2.5**)이 **미확정**이고, 확정 조건이 *"Phase 4 로 화면을 붙이고 **실제로 플레이해 본 뒤**"* 다 |
| `multi-combat-plan.md` §D8 | 자동 측정은 **동질 4인 팀**만 한다. *"실제 편성이라면 한둘만 범위를 들 것이므로 이 측정은 **범위 가치의 상한**"* |
| 같은 곳 | **혼합 편성은 ⛔ 기각** — *"편성 자체가 변수가 된다. 조합 폭발"* |

**⚠⚠ 모순처럼 보이는 이 두 줄이 이 화면의 존재 이유다.** §D8 이 혼합 편성을 기각한 것은 **자동 전수 측정**에서다 — 조합이 폭발하니까. 그런데 T 를 정하려면 바로 그 혼합 편성을 봐야 한다. **사람은 전수를 돌지 않는다.** 미리 정한 편성 몇 칸만 돌려 보고 판단한다(§9-5).

> 즉 이 화면은 §D8 을 어기는 것이 아니라 **§D8 이 구조적으로 못 하는 일을 한다.**

이 목적이 아래 모든 판단의 기준이다. **목적에 안 닿는 것은 전부 잘라낸다**(§7).

## 1. 화면이 반드시 답해야 하는 질문 다섯

목적에서 곧바로 나온다. 이 다섯에 답 못 하면 화면을 만든 의미가 없다.

| | 질문 | 화면이 있어야 하는 것 |
|---|---|---|
| ① | 4인 중 **범위 무공을 몇 개** 넣는 것이 이득인가 (0 / 1 / 2 / 4) | 슬롯마다 무공을 **따로** 고를 수 있어야 한다 |
| ② | 범위가 실제로 **몇 명**을 쳤는가 | 로그가 **대상별로** 보여야 한다 |
| ③ | 진형이 결과를 바꾸는가 (전2후2 / 전1후3 / 전4후0) | 슬롯마다 **열을 바꿀** 수 있어야 한다 |
| ④ | 던지기(후열 우선)가 값을 하는가 | ③ 과 같은 장치 + 로그에 **누가 맞았는지** |
| ⑤ | **여러 무공을 든 사람이 범위를 언제 고르는가** | 슬롯 하나에 무공을 **여럿** 넣을 수 있어야 한다 |

⚠ ①③ 이 *"슬롯 8개를 각각 만질 수 있어야 한다"* 를 강제하고, ⑤ 가 *"슬롯 하나가 무공 목록을 든다"* 를 강제한다.

### 1-1. ⚠⚠ ⑤ 를 빼면 이 화면은 자동 측정과 같은 맹점을 갖는다

`multi-combat-plan.md:327` 이 못박아 뒀다 — 동질 4인 팀은 *"각 전투원이 공격 초식 후보를 **1개만** 갖는 조건"* 이고,
그것은 §4-9-6 이 *"Sandbox·테스트 31곳 전부가 후보 1개라 `SelectArt` 의 순서 의존 결함이 안 보였다"* 고
지적한 **바로 그 조건**이다. 같은 문서 `:471` 은 *"**Phase 3 실전에서 문제가 된다** — 그때 다룬다"* 고 미뤄 뒀다.

**슬롯당 무공 1개로 만들면 이 화면도 정확히 그 조건을 재현한다.** 그러면 *"실전 플레이로 T 를 정한다"* 는
전제가 무너진다 — 자동 측정이 상한을 잰 이유(모두가 범위를 든다)를 하나 고쳤을 뿐, **다른 비현실(모두가
무공 하나만 든다)을 그대로 안고 가는 것**이기 때문이다.

→ **슬롯은 무공을 최대 3개까지 담는다.** 비용은 거의 같다(단일 값 → 짧은 목록). 그리고 이 화면이
`SelectArt` 를 **다중 후보로 실제로 돌려 보는 첫 자리**가 된다.

## 2. 플레이어의 결정은 **전투 전에 전부 들어간다**

작업공간 §8-3-2 — *"자동 전투를 쓴다면 결정은 전투 *전에* 전부 들어가야 한다."*

이 화면의 결정은 셋뿐이다: **무공 배정 · 열 배치 · 경지**. 전투가 시작되면 개입할 것이 없다.
→ 그래서 **실시간 진행이 필요 없다.** 전투를 즉시 끝내고 로그를 통째로 낸다(§7).

## 3. 구성

```
┌───────────────────────────────────────────────────────────────────┐
│ 전투 — 4대4                                    [1회] [100회]  경지 ▸ │
├──────────────────┬────────────────────────┬───────────────────────┤
│ 무공 고르기       │ 편성                    │ 결과 · 로그            │
│ (목록 화면 재사용) │                        │                       │
│  계층 ▸           │  A팀  전열 [ ][ ]       │  8경합, A 승 (2명 생존) │
│  유형 ▸           │       후열 [ ][ ]       │  ─────────────────    │
│  성향 ▸           │                        │  [1] A1 만우쾌사 →     │
│  ┌────────────┐   │  B팀  전열 [ ][ ]       │      B1 B2 B3 B4      │
│  │ 138종 목록  │   │       후열 [ ][ ]       │      피해 31·29·0·33  │
│  └────────────┘   │                        │  ...                  │
└──────────────────┴────────────────────────┴───────────────────────┘
```

- **슬롯을 누르면** 그 슬롯이 선택되고, 좌측 목록에서 무공을 누르면 **그 슬롯에 더해진다**(최대 3개)
- 슬롯 안의 무공을 다시 누르면 **빠진다**
- 슬롯의 **열 표시를 누르면** 전열↔후열이 바뀐다
- ⚠ 빈 슬롯을 허용한다 — *"3대4"* 같은 편성도 봐야 ①의 답이 나온다.
  ✅ 엔진이 받는다(`ResolveTeams` 는 각 팀 **1명 이상**만 요구하고 크기가 달라도 된다)

## 4. ⚠⚠ 가장 큰 위험 — **대전자를 만드는 규칙이 Sandbox 안에만 있다**

`Tools/Sandbox/Program.cs` 의 **private** 메서드 `ToCombatant(art, stage)` 가 규칙 셋을 들고 있다:

1. **경지 → 수련 횟수 환산은 성향마다 다르다** (정파 0.70/회 · 사파 1.60→소프트캡 후 1/5 · 마도 0.45)
2. **유형 숙달은 만렙 고정** — 무공 경지와 같이 움직이면 두 축이 섞인다
3. **강호무학은 성향이 없어 정파로 친다**

화면이 이것을 **다시 쓰면 갈라진다.** 이 저장소는 같은 형태를 이미 **다섯 번** 겪었다 — 상성·범위·열·종류(`MartialArtFactory`), 그리고 이번 작업의 이름표(네 곳 중복).

> **→ Core 로 올린다.** `Jianghu.Core.Combat.CombatantBuilder`(가칭). **Sandbox 가 그것을 쓰게 한다.**

⚠⚠ **Sandbox 를 건드리므로 §5-D 가 걸린다** — `--compare` 로 **바뀜 0건**을 확인하고, 안 그러면 원인을 밝힌다. 지난 커밋에서 같은 방식으로 이름표를 옮겼고 791건이 그대로였다.

## 5. ⚠⚠ 동명이인 — 로그가 누가 누구인지 못 밝힌다

`CombatLogEntry` 는 `ActorName` · `TargetName` **문자열**만 든다. 그런데 Sandbox 의 동질 팀은 **4명 전원이 무공 이름으로 불린다.** 그대로 두면 4대4 로그가 이렇게 나온다:

```
[2턴] 만우쾌사의 만우쾌사 → 만우쾌사 : 피해 31
```

**누가 누구를 쳤는지 읽을 수 없다.** ②④ 가 통째로 무너진다.

→ 화면은 대전자에게 **자리 이름**을 준다: `A1 만우쾌사` · `B3 궤암척혈`.
⚠ 이름은 `Combatant` 생성 시점에 정해지므로 **편성판이 만들 때** 붙인다. 엔진은 손대지 않는다.

## 6. **한 번으로는 T 를 못 정한다** — 반복 실행이 필요하다

1전투는 분산이 크다. **자동 측정도 4대4 를 40전씩 돌린다**(`Program.cs:1739` — 1대1 은 100전, `:25`).
사람이 1전투를 보고 판단하면 그 40전보다도 못한 표본으로 T 를 정하는 셈이다.

| 버튼 | 무엇 | 왜 |
|---|---|---|
| **1회** | 로그 전문 | ②④⑤ — *"범위가 몇 명을 쳤나"* · *"여러 무공 중 무엇을 골랐나"* 는 로그로만 보인다 |
| **1000회** | 승률 **± 표준오차** · 평균 경합 수 · 평균 생존자 | ①③ — 판단은 승률로 한다 |

⚠ **결정론 RNG 라 시드를 바꿔야 한다**(프로젝트 §1-2). 시드는 `1` 부터 1씩 올린다 — Sandbox 의
모든 측정 루프와 같은 관례라야 두 표를 나란히 읽는다. 고정 시드로 N번 돌리면 **같은 전투를 N번** 보는 것이고,
합계가 커져 통계처럼 보이지만 표본은 여전히 1이다.

### 6-1. ⚠⚠ 실측 — **문제는 실행 시간이 아니라 표본이었다** (2026-08-23)

2단계를 마치고 도구로 직접 쟀다. 원래 걱정은 *"100회가 프레임을 멈추는가"* 였는데 **틀린 걱정이었다.**

| 잰 것 | 결과 |
|---|---|
| 4대4 **100판** 실행 시간 | **약 25ms**(dotnet). ⚠ **Unity 안에서는 1000판 약 600ms** — 런타임이 달라 2.4배다(Play 실측). **다른 런타임의 측정치를 그대로 옮기지 않는다** |
| 거울 대진(같은 무공 4대4) **100판** | **43.0%** ← 50% 여야 하는 대진이다 |
| 같은 거울 대진 **500판** | **49.2%** (−0.4σ). 무공 5종 전부 46.4~52.0% 로 **편향 없음** |

**→ 43% 는 잡음이었다.** 100판의 1σ 가 **약 ±5%p** 라서 그렇다.

⚠⚠ **그러므로 `41% vs 43%` 같은 2%p 차이는 100판으로 판별할 수 없다.** 원래 계획대로 각 칸을
100회만 돌렸다면, T 를 **잡음을 보고 정할 뻔했다.** 실행이 싼 것을 확인했으니 판수를 올린다.

⚠ 화면은 승률 옆에 **표준오차를 함께 찍는다**(`TeamBattleSummary.StandardError`). 숫자 하나만
내놓으면 그 숫자를 믿게 되고, 그것이 §5-D 가 경계하는 형태다.

### 9-4. ✅⚠⚠ 곁가지로 얻은 것 — **Unity 층을 Unity 없이 컴파일하는 검사** (2026-08-23 신설)

3단계를 넘기기 전 *"컴파일을 미리 잡을 방법이 없나"* 를 찾다가 나왔다. **있었다.**

Unity 에디터 설치본에 **`UnityEngine.*` 모듈 DLL** 과 **uGUI 소스**가 통째로 들어 있다.
그 둘을 끌어와 `Assets/Scripts/{Core,Unity}` 를 함께 컴파일하는 csproj 를 만들었다 —
`Tools/UnityLayerCheck/`. **약 1초 · 사용자 개입 0.**

⚠⚠ **프로젝트 §4 가 등재한 지뢰를 정면으로 깎는다** — *"Unity 층은 1순위 검증이 안 닿는다"*.
이제 **컴파일 오류만큼은** 닿는다.

| | |
|---|---|
| ✅ 잡는다 | 없는 멤버 · 틀린 시그니처 · 오타 · 잘못된 enum 값 · 빠진 using · C#9 초과 문법 |
| ⛔ 못 잡는다 | **asmdef 참조 누락** · 런타임 동작 · 레이아웃 · 널 참조 |

⚠ **도구가 진짜 잡는지 확인했다** — 결함 셋(`Slot.Rowww` · `BattleRowRule.Flip` · `AttackScope.One`)을
일부러 심었더니 **줄·열까지 짚어 잡았다.** 통과가 빈말이 아니다.

⚠⚠ **그래도 Play 를 대신하지 못한다.** 이 도구가 오류 0 을 낸 코드에 **필터를 누를 때마다 슬롯에
무공이 담기는** 실행시 결함이 남아 있었다(코드를 읽다가 찾았다). 목록 화면에서 나온 결함 5건 중
넷이 Unity 층이었는데, **그중 컴파일로 잡혔을 것은 하나도 없다** — 전부 레이아웃·표시 논리였다.

### 9-5. ⚠⚠ 플레이 전에 **편성 표를 미리 적는다** (2026-08-23 실제 무공으로 확정)

*"몇 가지 골라 본다"* 로 두면 **보고 싶은 결과가 나오는 편성만 보게 된다.** §5-D 가 겪은
**선택적 관찰**의 다른 얼굴이다. 그래서 칸을 **먼저 확정하고 전부 돌린다.**

#### ⚠⚠ 먼저 — **범위 무공은 6종뿐이고 `다(多)` 는 0종이다** (2026-08-23 전수 실측)

| 범위 형태소 | 대상 | 종수 | 무공 |
|---|---|---|---|
| **다(多)** | 2인 | **0종** | — |
| 군(群) | 3인 | 3 | `정천창군`(소림사·창·정) · `후참혈군`(서량군문·도·사) · `환벌혈군`(사도련·도·사) |
| 전(全) | 전원 | 1 | `궤격비전`(천마신교·권·마) |
| 만(萬) | 전원 | 2 | `환창혈만`(혈교·창·마) · `만우쾌사`(사천당가·비도·정) |

**⛔ `다(多)` 를 쓰는 무공이 하나도 없다.** 즉 **2인 범위는 이 화면으로 검증할 수 없다.**
`다` 도 `T` = 1.15 를 쓰므로 군(群) 측정이 옮겨 붙는다고 **가정**할 수밖에 없다 — 가정이라고 적어 둔다.

#### ⭐ 완벽한 대조 짝 하나를 찾았다 — `환몽자혈` ↔ `환창혈만`

| | 환(幻) | 2번째 | 3번째 | 4번째 | 기력 |
|---|---|---|---|---|---|
| **`환몽자혈`** | 기만 | **몽(夢) 배경어 · 수치 0** | 자(刺) 찌르기 | 혈(血) 출혈 | 9 |
| **`환창혈만`** | 기만 | 창(槍) 찌르기 | 혈(血) 출혈 | **만(萬) 범위** | 36 |

⚠ **자(刺)와 창(槍)은 사전에서 같은 행**이다(`자창` — 찌르기). 즉 두 무공은 **배경어 하나가
범위 하나로 바뀐 것**이고, 비범위 축이 **완전히 같다**(공격 +0.75 · 명중 +10%p · 속도 +1 · 출혈 +10%p).
→ **범위 만(萬)의 순수 효과를 재는 자리다.** 같은 문파·유형·성향·글자수까지 맞는다.

군(群) 쪽에서 가장 가까운 짝은 **`중명벌혈` ↔ `후참혈군`**(둘 다 서량군문·도·사·4자·기력 12).
비범위 축이 `공격 +3 · 속도 −2 · 출혈` 로 같고 **`중명벌혈` 에 치명률 +10%p 가 더 있다** — ⚠ 완벽하진 않다.

#### ⚠ 화면에서 찾는 길 — **필터 경로** (프로젝트 §6-1)

목록에 검색창이 없다. 세 축을 전부 걸면 1~5종으로 줄고, **짝인 무공은 나란히 온다.**

| 계층 | 유형 | 성향 | 남는 것 |
|---|---|---|---|
| `대문파·세력` | `창` | `마도` | **2종** — ①`환몽자혈` ②`환창혈만` ⭐ **짝이 한 화면에 다 있다** |
| `대문파·세력` | `도` | `사파` | **3종** — ①`중명벌혈` ②`후참혈군` ③`환벌혈군` ⭐ **역시 나란히** |
| `전승무학` | `검` | `정파` | 2종 — ②`제화정참` (기본 편성에 들어 있는 것) |
| `대문파·세력` | `창` | `정파` | 3종 — ①`중뇌창` ②`정천창군` |
| `대문파·세력` | `권` | `마도` | 5종 — ⑤`궤격비전` |
| `전승무학` | `비도` | `정파` | **1종** — `만우쾌사` |

#### 돌릴 칸 — **B팀은 전 칸 고정. 경지 10성. 각 칸 1000회**

⚠⚠ **슬롯에 무공을 둘 담는 칸이 핵심이다.** 하나만 담으면 자동 측정과 같은 맹점(§1-1)이라
거기서 나온 T 는 실전값이 아니다. *"둘 다 든 사람이 범위를 고르는가"* 가 질문 ⑤ 다.

| 칸 | A팀 | B팀(고정) | 무엇을 보나 |
|---|---|---|---|
| **1** | `환몽자혈` ×4 | `환몽자혈` ×4 | **기준선**(거울) |
| **2** | A1 만 `환몽자혈`+`환창혈만`, 나머지 `환몽자혈` | 〃 | ⭐ **범위를 든 사람이 하나.** T만 판단의 중심 |
| **3** | A1·A2 가 둘 다 보유 | 〃 | 늘수록 이득이 붙는가 |
| **4** | 4인 전부 둘 다 보유 | 〃 | 상한 |
| **5** | 4인 전부 **`환창혈만` 만** | 〃 | **자동 측정과 같은 조건** — 기존 측정과 잇는 다리 |
| **6** | 2번 편성 + 진형 **전1후3** | 〃 | ③ 진형이 답을 바꾸는가 |
| **7** | 2번 편성에서 **`1회`** 로 로그를 읽는다 | 〃 | ⑤ **`SelectArt` 가 범위를 실제로 고르는가** |
| **8~12** | 위를 `중명벌혈`/`후참혈군` 으로 반복 | `중명벌혈` ×4 | **T**(군, 1.15) 쪽 |

⚠ **7번이 앞을 다 무효로 만들 수 있다.** 둘 다 든 사람이 범위를 **한 번도 안 고른다면**
2~4번의 승률 차이는 범위의 값이 아니라 잡음이다. **로그를 먼저 읽는 것이 순서상 더 낫다.**

⚠ 기본 편성은 `제화정참` ×8 이므로, 1번 칸부터 **여덟 슬롯을 `환몽자혈` 로 갈아야 한다** — 슬롯을 누르고 `비우기` → 목록에서 고르기.
⚠ 각 칸에서 적을 것 — **승률 ± 표준오차 · 평균 경합 · 평균 생존**. 화면의 `편성` 블록을 함께 남긴다.
⚠⚠ **표준오차보다 작은 차이는 차이가 아니다.** 1000회의 1σ 는 약 ±1.6%p 다. 칸끼리 비교할 때
이 선을 **먼저 긋고** 읽는다. 1.6%p 로 못 가르는 것이 나오면 판수를 올려야 하는데, 실측 실행이
**1000판 약 600ms**(Unity 안)이라 5000판도 3초다.

## 9-6. ⛔⛔ **5단계가 막혔다 — 범위 무공이 선택되지 않는다** (2026-08-23 첫 플레이)

A1 에게 `환몽자혈` + `환창혈만` 을 함께 들려 1000판 돌렸다. A1 이 8,985번 행동하는 동안
**`환창혈만` 을 0회** 골랐다.

원인은 `SelectArt` 의 점수식이 **범위 대가는 곱하면서 대상 수는 안 곱하는** 것이다
(`CombatResolver.cs:1613`). 상세와 고칠 거리는 [`HANDOFF §4-17`](HANDOFF.md).

⚠⚠ **이 화면이 그 결함을 잡으려고 만든 것은 아니지만, 잡았다.** §1-1 에서 *"슬롯당 무공 1개면
자동 측정과 같은 맹점"* 이라며 슬롯이 여럿 담게 바꾼 결정이 **첫 `1회` 로그에서 값을 했다.**
1개짜리로 만들었으면 T 를 정하려다 잡음을 재고 끝났을 것이다.

→ **편성 표(§9-5) 2~4·6~7번 칸은 지금 돌려도 의미가 없다.** 엔진을 고친 뒤에 돈다.
⚠ 5번 칸(4인 전부 범위만)은 후보가 1개라 여전히 유효하다 — 자동 측정이 재던 것이 그것이다.

## 11. 미결 — **모르는 것을 모른다고 적는다**

1. ~~**100회 반복이 프레임을 멈추는가**~~ — ✅ **해소**(§6-1). 100판 약 25ms · 1000판 약 250ms.
   ⚠ 대신 **표본이 문제**라는 것이 드러나 판수를 100 → 1000 으로 올렸다. 걱정한 곳이 아니었다
2. **편성판의 무공 배정이 손에 붙는가** — *"슬롯 누르고 목록 누르기"* 가 자연스러운지는 만들어 봐야 안다
3. **`CombatantBuilder` 를 올릴 때 Sandbox 출력이 정말 안 바뀌는가** — 바뀌면 그것은 **옮기다 규칙을 흘린 것**이므로 원인을 밝히기 전에 넘어가지 않는다
4. **경지를 어디까지 열 것인가** — 1~10성 전부인지 3·6·10성만인지. 측정 관례는 3·6·10성이다
5. ⚠ **T 를 몇 회 플레이해야 정할 수 있는지 모른다.** 이 화면은 판단의 **도구**이지 답이 아니다
6. ⚠⚠ **슬롯 3개가 "실전" 에 충분한 수인지 모른다.** ⑤ 가 후보 1개 맹점을 없애기는 하지만,
   Phase 3 의 실제 제자가 무공을 몇 개 들지는 아직 정해지지 않았다. 3 은 **임시값**이다
7. ⚠⚠ **사람이 편성을 고르는 절차 자체가 확증편향에 열려 있다.** *"몇 가지 골라 본다"* 는
   무엇을 고를지에 대한 기준이 없고, 그러면 **보고 싶은 결과가 나오는 편성만 보게 된다.**
   → 대책은 §9-5 의 **미리 적는 편성 표**다. 플레이 전에 칸을 확정하고 **전부** 돌린다
